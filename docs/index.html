Option-Name Bias in Jev

An evaluation of whether the probability distribution returned by a choice question is influenced by the option key names themselves, independent of the content being classified. Conducted against jev‑1.13.0 over 273 option sets under a pre‑registered analysis plan.

§1

Summary

The choice endpoint returns a non‑uniform distribution when no option is favoured by the input. The size of the deviation is governed by the option key names, and ranges from negligible to severe.

The practical consequence is confined but real: where a classification is a close call, the key names can decide it. In a routing test on a genuinely borderline support ticket, numbered keys produced a different team depending only on which slot each team occupied.

This review also corrects a prior internal finding. An earlier exploratory pass attributed the effect to alphabetical ordering of option keys. That attribution does not survive a powered test; the mechanism is better described as a preference for specific leading tokens.

Guidance

R1
Do not use sequentially numbered option keys.The highest-magnitude failure mode, because two components stack. Applies to queue1, tier1, item1, option1.
R2
Populate the description for every option.The single change that moved the rotation test in §5 from unstable to stable. Bare null criteria leave the key name as the only signal.
R3
Avoid a leading a, 0 or 1 on exactly one key.Worth roughly 2× uniform on a low-signal question. Harmless if no option has one, or if the favoured option is the one you would pick anyway.
R4
Treat serialisation order as part of the request.Per F5, insertion order is an independent factor. If keys come from a database or a dictionary, that order is arbitrary and currently uncontrolled.
R5
Where keys must be opaque, mitigate rather than rename.For retrieval candidates or document IDs there is no good name available. Rotate candidates across two calls and average, or move the identifier into the description.
R6
Run the rotation test on your own traffic.Take a borderline case, rotate the options through the key slots, compare verdicts. Two API calls, and it converts this review's general result into your own exposure figure.
§3

System under test and method

The contract

A choice question supplies a criteria map from option key to an optional description, and receives back a probability distribution over those keys plus a winner. The documentation does not state any dependence on key naming.

Isolating the key names

To measure a naming effect, all other signal is removed. Every question in the primary experiment uses an identical state and identical instructions; only the option keys vary. With 16 interchangeable options and no information, a uniform response is 0.0625 per option. Deviation from that baseline is the measured quantity, reported throughout as a multiple of the uniform share.

Controls

Insertion order is randomised independently of sort order in every set, from a fixed seed. Without this the two are confounded and no test can separate them. Across each condition the correlation between insertion rank and alphabetical rank is within noise of zero (all |ρ| < 0.04, all p > 0.39).

Batches were drawn from a shuffle of all sets rather than condition by condition, so request composition cannot masquerade as a condition effect. Question keys are opaque (q0…q9) and carry no information about the condition.

Sample size

Jev is exactly deterministic — identical requests return bit‑identical numbers — so repeating a request yields no information. The sampling unit is a distinct option set, not an API call. n = 30 sets per condition follows from an exact binomial power calculation against a 1/16 null: >99% power against a true rate of 0.50, 80% power down to 0.23, sufficient headroom for Holm correction across six hypotheses, and a ±0.10 equivalence margin for the one hypothesis asserting an absence.

16 options rather than 8 is required by the gradient test: a per‑set Spearman on 8 options needs |ρ| ≥ 0.685 for significance, on 16 options only 0.497.

§4

Findings

F1Confirmed
A naming prior exists, and its magnitude is governed by key style

Across all five conditions the returned distribution departs from uniform. The departure is not constant: numbered keys concentrate 5.1× the uniform share on the top option, while mixed‑case keys show no detectable effect. Any single-condition estimate of "the" bias would therefore be misleading.

Evidence
numeric 31.9% · p = 8.5e‑6 uuid 15.9% · p < 1e‑12 words 10.2% · p = 0.0096 nonsense 7.4% · p = 0.037 mixedcase 6.3% · p = 0.57 (ns)
F2Confirmed
The prior tracks the absolute leading character, not alphabetical rank

A ranking mechanism predicts that the first-sorting option is favoured regardless of which letter it begins with. Partitioning the word-based conditions by the leading character of their first-sorting option falsifies that prediction.

Options beginning with a take 2.04× the uniform share. Options that sort first but begin with any later letter take 1.12×, with a 95% interval of [0.98, 1.25] that includes 1.00 — that is, no detectable effect. Rank position confers nothing; the specific character does.

Evidence
Welch t = 4.51 · p = 2.3e‑5 a‑initial n = 36 later‑initial n = 84 later vs 1.00: p = 0.085 (ns)
F3Confirmed
The ordering is not performed by a sort in server code

A byte‑wise sort — the default behaviour of Object.keys().sort() — places digit‑led and punctuation‑led keys ahead of all lowercase keys. If a sort were responsible, those keys would be favoured.

They are the least favoured. Digit‑led keys receive 0.63× the uniform share; capitalised keys, which a byte sort also places early, receive the most at 1.41×. The ordering of these four styles is not reproducible by any collation rule, and is consistent with the key strings being read rather than sorted.

Evidence
Capitalised 1.41× [1.25, 1.57] lowercase 1.08× [0.95, 1.22] _prefixed 0.88× [0.76, 1.00] digit‑led 0.63× [0.52, 0.74] n = 120 options each
F4Confirmed
Numbered keys produce the largest deviation, via two additive components

This is the condition with operational consequences, because sequentially numbered keys are a common convention. Because the test runs did not all begin at 1 — some started at 2, some at 3 — the effect decomposes.

An ordinal comparison: the lowest number present is favoured even when it is 2 or 3, at 4.3×. Runs beginning at 2 and at 3 behave identically (27.3% and 27.1%), so this is not a general preference for small magnitudes.

A token bonus: the literal 1 is worth a further 3.1× on top. Where a run begins at 1, the first option takes 83.1% of the distribution against a uniform 6.25%.

Evidence
run starts 1: 83.1% [80.5, 85.7] starts 2: 27.3% starts 3: 27.1% literal 1 bonus: Welch t = 27.1, p < 1e‑12 numeric vs lexicographic ρ: −0.68 vs +0.11
F5Contradicts pre-registered H3
Key insertion order is an independent factor and was not dominated by name order

The pre‑registered hypothesis H3 held that the effect follows sort order rather than the order keys are written in. It is not supported. On ordinary words, insertion rank is the stronger predictor of the returned probability (ρ = −0.290) than alphabetical rank is (ρ = −0.176), though the paired difference does not itself reach significance (p = 0.15).

The two factors also diverge by condition. On UUIDs, name order dominates decisively. On mixed‑case and numeric keys the name‑order correlation is positive — mass increases with alphabetical rank — while insertion order stays consistently negative across all five conditions.

Operationally: the order you serialise keys in is a second lever, and it is one most callers do not know they are pulling, since it is usually whatever order a database or dictionary returned.

Evidence
words: name −0.176, writing −0.290 paired diff p = 0.15 (ns) uuid: name −0.555, writing −0.201 writing order negative in 5/5 conditions
F6Confirmed
Effect size depends jointly on key style and option count

A prior internal pass reported that the alphabetically‑first option takes 0.787 of the mass at 8 options — far above the 1.6× measured here on ordinary words. Re‑sending that pass's three option sets reproduces its numbers almost exactly (0.85, 0.73, 0.82 against 0.83, 0.73, 0.80), so the original measurements were sound.

The discrepancy is explained by what those sets contained: keys such as aaa/bbb and tag_a/tag_b, which differ only by a single alphabet character. A 2×2 crossing key style against option count separates the two factors. Both matter; style is the larger term.

Evidence

F7Exploratory — post hoc
A single account fits all conditions: the favoured token is a canonical sequence head

The following was derived after inspecting the data and is offered as a working hypothesis, not a tested result. It is the simplest description consistent with F2, F3 and F4.

In every condition the favoured key is the one whose leading token marks the start of a familiar ordered sequence, and the effect is absent when no such token is present.

§5

Operational impact

The findings above use inputs with no discriminating content, which is the maximal-exposure case by construction. To estimate impact under realistic conditions, a single borderline classification was tested: a support ticket describing both an incorrect charge after cancellation and a sign‑in failure. Billing or technical support is a genuine judgement call.

The same ticket was submitted four times per key scheme, rotating which category occupied which key slot. A scheme that classifies on content returns the same answer in all four rotations.

§6

Threats to validity

Single model version

All measurements are against jev‑1.13.0 on one day. The effect sizes are properties of that snapshot and should be re-measured after a model update.

Maximal-exposure inputs

§3 uses inputs with no discriminating content. This is deliberate — it isolates the naming factor — but it is the worst case. Where options carry genuine semantics, semantics generally dominate, and the residual bias is smaller than the headline figures.

F7 is post hoc

The sequence-head account was derived after inspecting the data. It fits every condition measured, but it was not pre-registered and has not been tested against a prediction it could fail. It should not be relied on operationally.

Operational impact is n = 1

§4 tests one ticket under one taxonomy. It demonstrates that the failure mode reaches realistic inputs; it does not estimate its frequency on production traffic. R6 is the way to obtain that figure.

Output quantisation

Returned probabilities sit on a 0.01 grid, and an answer can shift by roughly one grid step depending on which other questions share the request. Batches were shuffled across conditions to decorrelate this, but it is not eliminated.

H3 was not supported

The pre-registered claim that sort order dominates writing order failed (F5). The headline naming result stands on F2 and F3, which do not depend on H3, but any model of the mechanism must account for both levers.

§7

Reproduction

Collection and analysis are separate programs. Every figure in this review re-derives from the saved NDJSON without an API key, so the analysis can be re-run or modified without touching the data.

npm run collect150 questions, 15 requests → data/raw.ndjson npm run followup123 questions, 13 requests → data/followup.ndjson npm run analyseRESULTS.md — the pre-registered tests npm run exploreEXPLORATORY.md — post hoc, F7

PREREGISTRATION.md was committed before data/ existed; the repository history establishes the order. Statistics are exact where exact tests exist: binomial tests against the 1/16 null, Clopper‑Pearson intervals, Welch t for unpaired comparisons, TOST for the one equivalence claim, and Holm correction across the six pre‑registered families. Total cost of the full run: 28 requests, 56,038 input tokens.
